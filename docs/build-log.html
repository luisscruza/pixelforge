How each step works, and why it's built that way

A Laravel + Inertia + Vue app that sends image generations to Pixelforge, charges users cost + 25%, and stays correct when the provider fails, retries, or sends webhooks twice and out of order. Updated as each step lands.

01

Tooling and guardrails

Done

Why first: the strictness has to be in place before the domain code is written. Turning PHPStan to max on finished code means rewriting it; turning it on first means every class is typed correctly from the start.

  • Postgres instead of SQLite. SQLite has no real decimal type: DECIMAL(20,12) is stored as a float and SUM() drifts. Postgres keeps money exact in storage and in aggregates.
  • PHPStan level max + Larastan. Any value from the API is mixed until proven otherwise, which forces explicit parsing at every boundary.
  • Rector + Pint using the nunomaduro starter kit's rules (final classes, strict types, strict comparison), plus Pint/phpdoc_type_annotations_only, so docblocks carry types only.
  • nunomaduro/essentials: immutable dates, strict models, unguarded models, fake sleep and blocked stray HTTP in tests.
  • Saloon for outbound HTTP. Each Pixelforge endpoint becomes a typed request class instead of ad-hoc Http:: calls.

02

Exact pricing

Done

The core rule: Pixelforge never returns a price, only token counts, and its costs are fractions of a cent. We compute every amount ourselves with exact decimals, and never round in storage.

CalculateProviderCost

What Pixelforge charges us: Σ tokens × rate ÷ 1,000,000. It takes the rates as an argument, because each generation is billed at the rates fixed when it was created, not today's.

ApplyMarkup

What the user pays: provider cost × 1.25, kept to 12 decimals. A 9-decimal cost × a 2-decimal markup needs at most 11, so 12 holds it exactly.

EstimateGenerationCost

Two numbers for the form: an expected price (reasoning at the midpoint of its range) and a maximum price (+15% text tokens, max reasoning). The maximum is what step 5 reserves from the balance.

Decimal::from()

The only place untrusted input becomes a BcMath\Number. Anything non-numeric throws, so a malformed payload can't silently become $0.

The docs' worst case, reproduced in a test

High quality, 1536×1024, a 400-character prompt and 2 reference images, with text and reasoning tokens at their maximum:

Token type Count Rate / 1M Cost (USD)
Input text: ceil(400 ÷ 4) = 100, +15% 115 5.00 0.000575000
Input image: 2 × 765 1,530 10.00 0.015300000
Output: high, 1536×1024 (exact) 6,450 40.00 0.258000000
Reasoning: high-quality maximum 8,000 12.50 0.100000000
Provider cost 0.373875000
User price (× 1.25) 0.467343750000

Why not floats: 0.1 + 0.2 in floating point is 0.30000000000000004. Across thousands of generations that drift would make our provider costs disagree with Pixelforge's /v1/usage, which the reviewers check. BcMath\Number gives 0.3.

03

Models and the Pixelforge client

Done

Outbox and inbox: we save our own record before talking to Pixelforge, and save every webhook before acting on it. Neither the outgoing request nor an incoming event can be lost or applied twice.

generations (the outbox)

Created as pending in the same transaction as the credit hold. Its uuid is the Idempotency-Key and is sent in metadata, so a retried POST returns the same Pixelforge generation and a webhook can find our row even before the POST returns.

webhook_events (the inbox)

The primary key is Pixelforge's evt_ id. A second delivery of the same event fails the insert at the database level, so it can never be recorded twice, even with two deliveries arriving at the same moment.

Money columns

estimated_price, maximum_price, provider_cost and price are all DECIMAL(20,12), read back through an AsNumber cast as BcMath\Number. A test round-trips 0.467343750001 to the last digit.

Status only moves forward

pending → queued → processing → succeeded | failed. GenerationStatus::canTransitionTo() refuses any step backwards and anything out of a final state. This is the rule that handles out-of-order webhooks.

The Saloon client

  • PixelforgeConnector holds the base URL, bearer key and timeouts (5s connect, 15s request), and always throws on 4xx/5xx. A failed call can never look like a success.
  • Typed methods: createGeneration(), generation(), pricing() and usage(). Each request class turns JSON into a DTO (GenerationData, PricingData, UsageDay), so no raw arrays leak into the app.
  • createGeneration() always sends the Idempotency-Key header and our generation_uuid in metadata. Empty metadata is sent as {}, not [], because Pixelforge rejects unexpected shapes with a 422.
  • PixelforgeException carries errorCode, retryAfterSeconds and isRetryable(). Rate limits, concurrency limits, overloads and any 5xx are retryable. Policy blocks, the daily quota, a bad key and idempotency clashes are not, because retrying can't fix them.
  • A test found that a non-JSON error body (a proxy's 502 Bad Gateway) crashed the parser. It now falls back to http_502 and is treated as retryable.
  • GetPricing caches /v1/pricing for 5 minutes, so the live estimate doesn't spend the 60 requests/minute that generations need. It was checked against the live endpoint.

04

Submission, webhooks and reconciliation

Done

Goal: reach the right final state no matter how Pixelforge behaves: overloaded, rate-limited, a webhook before the POST returns, duplicates, out of order, or no webhook at all.

Pixelforge says What we do User is charged
429 rate_limit_exceeded Release the job after Retry-After, with growing backoff, capped at a few attempts Nothing yet
429 concurrency_limit_exceeded Same; the row stays "queued" in our UI while it waits Nothing yet
503 overloaded Retry with the same Idempotency-Key Nothing yet
400 content_policy_violation Mark failed and show the reason $0, hold released
429 daily_limit_exceeded Mark failed; retrying today can't help $0, hold released
generation.failed Mark failed with the error code $0, hold released
generation.succeeded Store usage, compute cost at the generation's own rates Actual cost × 1.25, once
  • Duplicates: the event insert fails, so we answer 2xx and do nothing.
  • Out of order: a late processing after succeeded is refused by the forward-only rule.
  • Webhook before the POST returns: we match on metadata.generation_uuid, not just gen_.
  • Signatures: HMAC-SHA256 of t.body on the raw body, compared in constant time, rejected if more than 5 minutes off in either direction.

How it was built: four pieces, one commit each

ApplyGenerationSnapshot

The only code that changes a generation's state. Webhooks, the submit response and polling all go through it. It locks the row with SELECT … FOR UPDATE, so two simultaneous deliveries apply one after the other, and it prices a success once, at the generation's own rates.

Submission

CreateGeneration writes the pending row and dispatches the job after commit. SubmitGenerationJob waits max(Retry-After, 2^attempt) seconds, capped at 60, and keeps trying for 10 minutes. Then it marks the row needs_reconciliation, never failed. A duplicate job sends nothing because the row has already left pending.

Webhooks

A middleware checks the signature before anything else runs. The controller validates the event's shape and delegates. insertOrIgnore on the event id means only a first delivery queues processing. We reply 204 immediately, well inside Pixelforge's 10-second limit.

Reconciliation

pixelforge:reconcile runs every minute, never overlapping. It re-queues submitting/unknown rows idle for 2+ minutes, re-POSTs needs_reconciliation rows every 15 minutes with the same key, and polls up to 20 stuck in-flight rows. It stops as soon as Pixelforge rate-limits it.

A timeout is not a failure

When our POST times out, Pixelforge might never have received it, might have created the generation, or might have already finished it. We can't tell, so we never record that as failed. The provider's lifecycle (status) and our submission's state (submission_status) are separate columns, and only Pixelforge's own answer moves status.

Situation status submission_status Credits
Saved, POST not answered yet pending submitting Held
Timeout, or a 5xx with no Pixelforge error code pending unknown Held
Coded 429 / 503 overloaded (Pixelforge answered, created nothing) pending unchanged, retried Held
10-minute retry window used up pending needs_reconciliation Held
Pixelforge confirms (POST response, replay, webhook or poll) queued → processing accepted Held
Pixelforge: succeeded succeeded accepted Actual × 1.25, once
Pixelforge: failed, or a definitive refusal (400 policy, daily quota…) failed accepted / rejected $0, hold released
  • Recovery re-POSTs with the same key and payload. Pixelforge guarantees a repeated key returns the original generation and that keys never expire, so we don't need a lookup endpoint. If the original arrived, the replay returns its current state; if it didn't, the replay creates it.
  • needs_reconciliation is not terminal. The reconciler re-POSTs every 15 minutes until Pixelforge answers definitively. A late webhook can resolve it at any time, and it's billed exactly once through the same locked method.
  • A 429 on a replay proves nothing. Every retry counts against the per-minute limit, so being rate-limited doesn't mean the original never landed. It stays retryable and never fails the row.
  • No overwriting a success. Setting unknown or needs_reconciliation is a conditional UPDATE … WHERE status = 'pending'. If a success webhook landed while our POST was timing out, that update matches nothing. A test reproduces exactly this race.
  • The report's difference column is an alert, not an accepted loss. The spend report also counts unresolved submissions, so credits held on uncertain outcomes stay visible.

Balances and the admin report

Done

Hold the maximum, charge the actual. The final cost isn't known at submit time, so we reserve the most it could possibly cost. A user can never go negative, and nobody is overcharged.

The ledger: one generation's life in credits

Event Ledger entry Amount Balance
User buys credits purchase +1.000000000000 1.000000000000
Submits medium 1024×1024 (max $0.0875) hold −0.087500000000 0.912500000000
Pixelforge: succeeded release +0.087500000000 1.000000000000
Actual cost $0.056515 × 1.25 charge −0.070643750000 0.929356250000
Same success delivered again nothing (unique index) 0 0.929356250000
  • The balance is SUM(amount) over an append-only ledger. It's never overwritten, so every cent can be traced to a line.
  • A unique index on (generation_id, type) means Postgres itself refuses a second hold, release or charge for one generation.
  • Submitting locks the user row, checks balance ≥ maximum price and writes the hold, all in one transaction. Two tabs can't both spend the last dollar.
  • Settlement runs in the same transaction as the status change, in both ApplyGenerationSnapshot and MarkGenerationAsFailed, so status and money can never disagree.

The spend report

  • Groups succeeded generations by UTC day of completed_at. A generation started at 23:59:50 and finished after midnight counts on the next day, the same day Pixelforge bills it.
  • Every day in the range is included, even with zero usage, so it lines up row for row with /v1/usage. Each day shows charged, provider cost, profit, a per-user breakdown, Pixelforge's cost_usd and the difference. Per-user totals are ranked by spend.
  • If /v1/usage is unavailable, the report still shows our own numbers and marks the comparison unavailable.
  • Admins have an is_admin flag and a viewSpendReport Gate. The buy-credits and report pages arrive in step 6.

06

InteriorIA: the interface

Done

The product: InteriorIA is an AI interior designer, with Pixelforge as the engine behind it. The look is soloterm's blue on an architect's blueprint grid, which reads as graph paper for room plans.

One studio page

The prompt form sits next to your designs. Room and style presets fill in the prompt, and inspiration photo URLs are optional. A collapsible panel inserts Pixelforge's test keywords, so reviewers can trigger every failure path.

Optimistic submit

<Form :optimistic> inserts a "sending" card at the top of the feed and deducts the maximum price from the shown balance instantly. A validation error, such as not enough credits, rolls both back automatically.

Live without breaking the scroll

usePoll runs only while something is in flight, in rest mode, paused in background tabs. It asks for an Inertia::optional() prop of just the watched cards and overlays them, so the infinite-scrolled history is never reset.

Exact estimate in the browser

The estimate uses BigInt integer math (cost × 10⁸), so it matches the PHP side to the last digit: 0.46734375 for the docs' worst case. The server still recomputes on submit.

Inertia v3 features used

createForm<T>() and useFormContext<T>() for typed forms, plus Inertia::scroll with <InfiniteScroll>. Stats and the report use Inertia::defer, and the report adds rescue with a retry button. Pricing is an Inertia::once prop. Navigation uses instant visits and prefetch, the draft persists through useRemember, and buying credits is an optimistic router.optimistic().

Small pieces

Pure helpers live in lib/ (money, time, studio presets). Reactive logic lives in composables (useCostEstimate, useGenerationFeed, useCredits, useNow…). Components are grouped by feature, and pages only compose them. There are skeletons for every deferred or loading state, plus an empty state, and motion respects reduced-motion settings.

Bug found on the way: Laravel 13 refuses to unserialize objects from the cache by default. The cached pricing DTO came back as __PHP_Incomplete_Class on the database cache. The tests use the in-memory array cache, which never serializes, so they missed it. Pricing is now cached as the documented array shape, and a regression test runs through the file cache.
